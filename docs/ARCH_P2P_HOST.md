# 让房主当服务器（P2P 直连模式）可行性方案

## 实现状态（2026-11-17）

| 步骤 | 状态 |
| --- | --- |
| 1. 抽 `src/lib/roomCore.ts`（纯 TS，三端共用） | ✅ 完成 |
| 2. `server.ts` / `worker/index.ts` 改为委托 RoomCore | ✅ 完成，回归测试全绿（协议单测 24/24、workerd e2e 15/15、Express 9/9） |
| 3. `src/lib/p2pRoom.ts` + `App.tsx` 传输层接入 | ✅ 代码完成，未在真实双设备浏览器里验证 |
| 4. 房主离开提示 / 状态恢复 | ✅ 完成：房主断开时客人提示「房主已离开，已切回云端房间」；房主 5 秒一次把场景/视频/聊天存 localStorage，刷新后恢复；房主刷新后靠 `p2p:host` 重新认领身份（sessionStorage 记住「我曾是房主」） |

**怎么用**：在房间链接后面加 `&p2p=1`，例如
`https://kokospace.de5.net/?room=abc&p2p=1`。
先进入的人是房主（云端 `hostId`），其余人自动连房主；连不上会自动回落云端房间（会弹提示）。

**已知未覆盖**：房主刷新 / 换设备后 `hostId` 会变，此时新客人可能找错房主。步骤 4 会一起解决。

### 其他设备怎么连上房主（操作三步）

1. **房主先进**：打开 `…/?room=<房间号>&p2p=1`，选形象进入。第一个进来的人自动成为房主。
2. **房主复制链接**：右上角「复制邀请链接」——P2P 模式下会自动带上 `&p2p=1`（少了这个参数，别人会进云端模式，连不到房主）。
3. **其他设备打开这个链接**：自动发起连接，成功会弹「已直连房主，延迟更低」。

房间号必须一致；房主必须先到（云端按「第一个进房的人」判定 hostId）。

### 内部发生了什么

```
客人设备                         云端（WebSocket）                        房主设备
   │ 1. join(room) ───────────────▶│
   │ 2. ◀──────────── room:init {hostId}
   │ 3. p2p:signal（SDP/ICE）──────▶│──────── 转发 ────────▶ 房主
   │ 4. ◀────────────────────────── 转发 ──────────────────│
   │ 5. ══════ WebRTC DataChannel（设备 → 设备，直连）══════
   │ 6. join 走数据通道 → 房主回 room:init（真正的房间状态）
```

第 1–4 步只用几秒，之后所有消息（位置、聊天、视频进度）都不再经过云端。

### 三种网络的实际结果

| 场景 | 结果 | 延迟 |
| --- | --- | --- |
| 同一 WiFi | 必通 | 5–20ms |
| 手机 4G ↔ 家里宽带 | 多数能通（STUN 打洞） | 30–80ms |
| 公司 / 校园 / 酒店网 | 常见失败（对称 NAT） | 回落云端，150–400ms |

失败时页面会弹「直连失败，已切回云端房间」，功能不受影响，只是回到云端延迟。要兜住这部分需要配 TURN：

```
VITE_TURN_URL=turn:turn.example.com:3478
VITE_TURN_USER=用户名
VITE_TURN_PASS=密码
```

配了之后 `p2pRoom.ts` 会自动带上，构建时注入即可（Cloudflare Calls 有免费额度，也可以自建 coturn）。

### 实测怎么验（两台设备）

1. 电脑开 `…/?room=test&p2p=1`，选形象进入 → 第一个进来的人是房主
2. 手机开同一个链接（同房间号）→ 应弹「已直连房主，延迟更低」
3. 两边走动、发消息、拖播放进度 → 另一台应即时跟手
4. 关掉房主页面 → 客人应弹「房主已离开，已切回云端房间」，房间继续可用（走云端）
5. 房主刷新页面 → 场景/视频/聊天从 localStorage 恢复

判断延迟：P2P 下移动已经不用等跨洋 RTT，同城应在 30ms 量级；如果还是几百毫秒，说明实际走了云端（看有没有弹「已直连房主」）。

### 上线后踩过的两个坑（2026-11-19 修复）

**1. 房主 6 秒自杀 → 全房间回落云端**

`App.tsx` 里 `armP2PFallback()` 会在 6 秒内没建好直连时回落云端。问题是房主也被套上了这个定时器：
房主进房时房间里还没有客人，`P2PRoom.connected` 对房主判的是 `status === 'connected'`，
而房主只有在 `dc.onopen` 时才置 connected —— 于是房主进房 6 秒后必然判定「超时」，
`fallbackToCloud()` 把 `p2pEnabledRef` 关掉、把 `p2pRef` 关闭。之后客人再进来发的 `p2p:signal`
就没人处理了（`p2pRef.current` 是 null），表现就是**线上永远是云端模式**。

本地测不出来：loopback 建连 < 1 秒，房主的定时器还没到就已经有 peer 了。
线上跨洋建连要 3–4 秒，正好卡在 6 秒边界。

修法：`P2PRoom.start()` 里房主直接 `setStatus('connected')` —— 房主本身就是权威，不存在「连不上自己」。
另外 `pc.onconnectionstatechange` 里区分角色：只有客人失败才回落，房主侧单个 peer 失败只打日志。

**2. STUN 列表全是海外地址**

原来只配 `stun.l.google.com` / `stun1.l.google.com`。国内不可达，浏览器要等 6 秒超时才收集完候选，
本身就超过 6 秒的直连阈值。

实测（国内家宽）后改成 `src/lib/rtcConfig.ts` 统一维护：

| STUN | 耗时 | 结论 |
| --- | --- | --- |
| `stun.miwifi.com:3478` | 137ms | 主力 |
| `stun.douyucdn.cn:18000` | 138ms | 备用 |
| `stun.chat.bilibili.com:3478` | 954ms | 第三 |
| `stun.cloudflare.com:3478` | 6703ms | 弃用，UDP 绕路 |
| `stun.qq.com:3478` | 6007ms | 已失效 |
| `stun.l.google.com:19302` | 6003ms | 仅海外兜底 |

状态通道和空间语音共用这一份配置，别再各写一份。

## 结论

**可行，而且对这个项目特别合适** —— 因为视频不是我们中继的：YouTube / Bilibili 是 iframe 各自播放，
mp4 是直链各自下载，我们只在 P2P 上跑 JSON（位置、聊天、播放进度）。一条 `player:move` 约 100 字节，
6 人 × 10 次/秒 ≈ 6KB/s，房主家里宽带完全扛得住。

收益：同城延迟 **10–40ms**（现在是 342–1165ms），服务器成本 **0**。
代价：**房主关页面 = 房间结束**；约 **10–20%** 的网络组合打不通（需要 TURN）；改造约 **3 天**。

## 拓扑

```
        ┌──────────── Cloudflare（只做信令 + 静态资源，几秒就用完）────────────┐
        │                                                                      │
   房主浏览器                                    客人 A            客人 B
   ┌──────────────────┐                     ┌──────────┐      ┌──────────┐
   │ LocalRoom（权威） │◀── DataChannel ────▶│ 客户端    │      │ 客户端    │
   │ 位置/视频/聊天    │◀── DataChannel ─────────────────────▶│          │
   └──────────────────┘                     └──────────┘      └──────────┘
```

- 客人之间不直连（星型），消息顺序只在房主一处决定，不会出现「谁说了算」的冲突。
- WebSocket 只在建立连接的那几秒用到：交换 SDP / ICE。那次握手慢 1 秒无所谓，之后一律走 P2P。
- 语音保持现状（已有的 `SpatialAudioManager` 就是 P2P mesh），不动。

## 三个必须承认的限制

1. **信令仍要一个云端**（Cloudflare 就行）。它只在握手时用，不承担实时流量，
   所以即使慢 1–2 秒也不影响手感。想彻底不要云端只能手动复制粘贴 SDP，不现实。
2. **NAT 穿透**：STUN 免费能覆盖大部分家庭宽带；对称 NAT / 公司网 / 部分 4G 会失败（经验值 10–20%）。
   要兜住这部分需要 TURN —— 可以用 Cloudflare Calls 的 TURN 免费额度，或自建 coturn（一台小机器）。
   建议：UI 上加「直连/P2P 失败 → 自动回落到云端房间」。
3. **房主就是单点**：房主网络抖动，所有人一起卡；房主关页面，房间结束。
   这是 P2P 模式的固有代价，换来的是零成本 + 低延迟。

## 推荐落地顺序

1. 先做步骤 1（抽 `RoomCore`），这一步纯重构，不改行为，现有 24 项协议测试可以直接复用。
2. 再做步骤 2 + 3，加一个「直连模式」开关，默认仍走云端，成功建链后才切。
3. 步骤 4 收尾，加房主离开提示与状态恢复。

保留现有 Cloudflare 房间模式作为兜底，**不要删**。两条路并存：
`?room=xxx&p2p=1` 走直连，`?room=xxx` 走云端。

## 和「买香港服务器」比

| | P2P 房主模式 | 香港轻量 + Docker |
| --- | --- | --- |
| 同城延迟 | 10–40ms | 30–80ms |
| 成本 | 0 | ¥24–60/月 |
| 上线时间 | 约 3 天改造 | 30 分钟 |
| 稳定性 | 受房主网络与 NAT 影响 | 稳定，7×24 |
| 房主离线 | 房间关闭 | 无影响 |

如果只是自己几个朋友用一个房间，P2P 更划算；如果要长期给别人用的公共房间，服务器更靠谱。

## 房主掉线时会发生什么

| 场景 | 客人感知 | 房间内容 |
| --- | --- | --- |
| 房主关标签页 / 正常关浏览器 | DataChannel 立刻 close，秒级 | 保留（云端有镜像） |
| 房主直接关机 / 拔网线 | 心跳 7 秒超时 | 保留（最多落后 5 秒） |
| 房主切到别的标签页 | 无感知 | — |

两条机制配合：

1. **反向心跳**（`p2pRoom.ts` 的 `startWatchdog`）：客人每 2 秒发一次
   `p2p:ping`，房主在 DataChannel 的 `onmessage` 里直接回 `p2p:pong`。
   之所以不反过来让房主定时发，是因为后台标签的 `setInterval` 会被浏览器
   节流到 1 分钟一次，房主切个标签页就会把所有人误踢回云端；而
   `onmessage` 是网络事件，不受节流影响。
2. **状态镜像**（`room:snapshot`）：房主每 5 秒把 `RoomCore.exportState()`
   通过云端 WS 发给服务端，服务端只在发送者确实是当前房主时
   `restoreState`。房主挂掉后，云端房间不是空的，接管的人打开就是同一部片、
   同一个进度、同一段聊天。

不能解决的部分：房主的浏览器没了，本地 `localStorage` 也一起没了；
状态在云端只是「副本」，接管的人只能继续播，不能替房主恢复它的本地设置。
